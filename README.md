## Что это такое

Это учебный Java-проект, реализующий **марковский процесс принятия решений (MDP)** и
**policy iteration** для классической задачи «агент в стохастической сетке»:

- мир размером `4 × 3`;
- агент стартует в `(1,1)`;
- цель `(3,4)` даёт награду `+1` и завершает эпизод;
- штраф `(2,4)` даёт `-1` и завершает эпизод;
- клетка `(2,2)` — стена, вход запрещён;
- каждый обычный шаг стоит `-0.04`;
- действия стохастические: с вероятностью `0.8` агент идёт туда, куда хотел,
  с вероятностями `0.1` и `0.1` его сносит влево/вправо.

Программа умеет:

1. Строить **оптимальную политику** через `policy iteration`.
2. Считать **полезности состояний** `U(s)`.
3. Проверять результат через независимый `value iteration`.
4. Показывать всё в **Swing-окне**: сетка, награды, стрелки политики, значения `U`,
   положение агента и его след; агент может двигаться по обученной политике.
5. Выводить таблицы в консоль и прогонять **SelfTest** без JUnit.

Проект использует только стандартную библиотеку Java. Внешних зависимостей нет.
Код рассчитан на Java 17+; фактическая проверка выполнялась на JDK 26.

## Зачем это нужно

Проект демонстрирует полный цикл решения MDP:

- формализацию среды (состояния, действия, награды, переходы);
- учёт стохастичности и «сносов»;
- понятие **proper policy** — политики, которая гарантированно достигает цели;
- **policy evaluation** — решение линейной системы через итерации Беллмана;
- **policy improvement** — жадное улучшение по Q-значениям;
- сходимость **policy iteration** и перекрёстную проверку через **value iteration**;
- визуализацию политики и полезностей в реальном времени.

Отдельный важный момент: при `gamma = 1.0` любая политика, которая может
зациклиться и никогда не достичь терминального состояния (**improper policy**),
ломает оценку — ряд полезностей расходится. Поэтому начальная политика строится
не «наугад», а через **BFS от цели**. Это гарантирует, что стартовая политика
является proper, и policy iteration сходится.

Эталонные числа и политика взяты из постановки лабораторной. При этом переходы
**не хардкодятся формулами из PDF**: все они вычисляются через единый метод
`Environment.getTransitionProbabilities(s, a)`.

## Точка входа и режимы запуска

Единственная точка входа — **`lab5.Main.main(String[] args)`**
([`src/lab5/Main.java:17`](src/lab5/Main.java)).

Алгоритм выбора режима:

```text
Main.main(args)
├── есть "--list-envs" -> печать встроенных сред -> завершение
├── есть "--test"      -> SelfTest.main(args) -> завершение (exit code 0/1)
├── есть "--console"   -> env = new Environment(resolveEnvironment(...));
│                         env.validate(); runConsole(env)
└── иначе               -> env = new Environment(resolveEnvironment(...));
                          env.validate();
                          SwingUtilities.invokeLater(() -> new Visualizer(env).setVisible(true))
```

Поддерживаемые аргументы:

| Аргумент              | Что делает                                                        |
|-----------------------|-------------------------------------------------------------------|
| `--test`              | Запускает `SelfTest`: все проверки, `[PASS]/[FAIL]`, код `1` при ошибке |
| `--console`           | Обучает агента и печатает `U`, политику, итерации, путь и Q-значения |
| `--env=ID`            | Выбирает встроенную среду: `classic`, `open`, `maze`, `wide`       |
| `--env-file=ПУТЬ`     | Загружает собственную среду из текстового файла                    |
| `--random`            | Генерирует новую случайную среду при каждом запуске                |
| `--random=SEED`       | Случайная среда, воспроизводимая по seed                           |
| `--delay=МС`          | Стартовая задержка между шагами агента в GUI, 30…2000 (по умолчанию 450) |
| `--list-envs`         | Печатает список встроенных сред и завершает работу                 |
| *(нет)*               | Открывает Swing-визуализацию (среда `classic`)                     |

Порядок приоритетов: `--list-envs` и `--test` завершают работу до выбора среды;
`--env-file` важнее `--env`. Если среда не найдена или файл некорректен, программа
печатает ошибку и завершается с кодом `2`.

Важно: в режимах GUI и консоли `env.validate()` вызывается **до** любой работы с
моделью. В режиме `--test` та же проверка выполняется первым тестом `SelfTest`.

### Направление зависимостей и роли

| Класс | Роль | От кого зависит | Кто использует |
|-------|------|-----------------|----------------|
| `State` | значение-координата | — | все |
| `Action` | значение-действие | — | `Environment`, `Agent`, GUI |
| `EnvironmentConfig` | неизменяемое описание среды: размеры, особые клетки, награды, вероятности; пресеты и разбор текста | `State` | `Environment`, `Main`, `Visualizer`, `SelfTest` |
| `RandomEnvironment` | генератор случайных сред с гарантией играбельности | `EnvironmentConfig`, `Environment`, `Agent`, `State`, `Action` | `Main`, `Visualizer`, `SelfTest` |
| `Environment` | **единственный источник истины** о MDP | `EnvironmentConfig`, `State`, `Action` | `Agent`, `Visualizer`, `Main`, `SelfTest` |
| `Agent` | алгоритмы обучения и движения | `Environment`, `Action`, `State`, `StepResult` | `Visualizer`, `Main`, `SelfTest` |
| `StepResult` | DTO одного шага | `State`, `Action` | `Agent`, `Visualizer` |
| `Visualizer` | GUI и управление эпизодом | `Environment`, `EnvironmentConfig`, `Agent`, `StepResult`, `State`, `Action` | `Main` |
| `Main` | выбор режима и среды | `Environment`, `EnvironmentConfig`, `Agent`, `Visualizer`, `SelfTest` | — |
| `SelfTest` | проверка инвариантов и эталонов | все | `Main` |

Ключевой принцип: **`Agent` не знает конкретных координат и вероятностей**. Он всегда
спрашивает среду через `env.getTransitionProbabilities(s, a)`, `env.reward(s)`,
`env.intendedNextState(s, a)` и `env.getActions(s)`. Благодаря этому переходы
вычисляются в одном месте и не дублируются ошибочными формулами.

Параметры строения среды (размеры, особые клетки, награды, вероятности) вынесены
в `EnvironmentConfig`. `Environment` — тонкая модель, читающая эти параметры.
Благодаря такому разделению **одни и те же алгоритмы `Agent` работают на любой
сетке**: классической 4×3, лабиринте 6×5, широкой 6×4 или собственной карте из
файла.

### Потоки данных

#### Обучение (policy iteration)

```text
Environment.validate()
        │
        ▼
Agent.policyIteration()
        │
        ├─ initializeUtility():  терминалы -> R(s), остальные -> 0
        ├─ initializePolicy():   BFS от цели, proper policy
        │
        └─ цикл:
              evaluatePolicy()   -> utility (итерации Беллмана)
              improvePolicy()    -> greedy argmax Q(s,a)
              changes == 0 ?     -> converged = true, выход
```

#### Один шаг агента

```text
Visualizer.performStep()
        │
        ▼
Agent.step(currentState)
        │
        ├─ decide(state)                 -> policy.get(state) / NONE
        ├─ move(state, action)           -> env.sampleNextState(state, action, random)
        └─ new StepResult(from, action, to, env.reward(to))
        │
        ▼
Visualizer обновляет currentState, след, суммарную награду, статус, repaint()
```

#### Отрисовка

`GridPanel` — внутренний класс `Visualizer`. Он хранит ссылки на `Environment` и
`Agent`, текущее состояние и список посещённых состояний (`trail`). При
`paintComponent` он читает `agent.getUtility(s)` и `agent.getPolicy(s)` **только
если обучение уже завершено** (`trained == true`). Это исключает показ
промежуточных значений как «оптимальных» и избегает чтения карт агента во время
фонового обучения.

## Смена окружения

Среда больше не прибита к координатам в коде. Её описание вынесено в
[`EnvironmentConfig`](src/lab5/EnvironmentConfig.java), а `Environment` строится
по этому описанию. Есть четыре способа сменить окружение.

### 1. Выбор в GUI

Над сеткой появилась строка «Среда:» с выпадающим списком и кнопками
**«Своя среда...»** и **«Случайная среда»**:

- список содержит встроенные пресеты (`Классическая 4×3`, `Открытая 4×3`,
  `Лабиринт 6×5`, `Широкая 6×4`) и все среды, созданные в этом сеансе;
- **«Случайная среда»** генерирует новую карту (см. ниже) и сразу делает её
  активной; каждое нажатие даёт другую среду, а сгенерированная карта остаётся в
  списке, пока открыто окно;
- при выборе другого пункта модель и агент пересоздаются, обученная политика
  сбрасывается, агент возвращается в старт;
- **«Своя среда...»** открывает файловый диалог и загружает текстовое описание
  (см. формат ниже); после загрузки среда сразу становится активной и появляется
  в списке;
- если файл или карта некорректны, показывается сообщение об ошибке, а текущая
  среда остаётся прежней.

Переключение среды, загрузка и генерация заблокированы, пока идёт обучение.

### Регулировка скорости агента

Внизу окна, под кнопками, есть ползунок **«Скорость»**:

- диапазон — от `2000` мс/шаг (медленно, `0.5` шаг/с) до `30` мс/шаг (быстро,
  `33.3` шаг/с), по умолчанию `450` мс;
- подпись рядом показывает текущую задержку и скорость в шагах в секунду;
- шкала логарифмическая, поэтому и на медленном, и на быстром конце ползунок
  ощущается плавным;
- скорость меняется **на лету**: если агент уже идёт, таймер перезапускается с
  новой задержкой, останавливать эпизод не нужно;
- выбранная скорость сохраняется при «Сбросе» и при смене среды;
- стартовое значение можно задать аргументом `--delay=МС`.

С точки зрения кода это `javax.swing.Timer`: `speedChanged()` переводит позицию
ползунка в задержку (`sliderToDelay`), обновляет `timer.setDelay()` и
`setInitialDelay()`, а при запущенном эпизоде вызывает `timer.restart()`.

### Встроенные среды

| Id | Название | Размер | Особенности |
|----|----------|--------|-------------|
| `classic` | Классическая 4×3 | 4×3 | стенa `(2,2)`, как в лабораторной |
| `open` | Открытая 4×3 | 4×3 | та же сетка без стены |
| `maze` | Лабиринт 6×5 | 6×5 | четыре стены, коридоры |
| `wide` | Широкая 6×4 | 6×4 | три стены, длинный путь |

### Случайная генерация

[`RandomEnvironment`](src/lab5/RandomEnvironment.java) строит новую карту при
каждом вызове. Размер — от `4×3` до `8×6`, плотность стен — `15…30 %`,
вероятности — одна из пар `0.70/0.150 … 0.90/0.050`.

Генерация не «кидает кубик» до победного конца: каждая карта проходит проверки,
и неудачная раскладка отбрасывается и генерируется заново (до 300 попыток).

Гарантии принятой среды:

1. **Старт, цель и штраф** различны, внутри сетки и не являются стенами;
   цель удалена от старта минимум на 3 клетки манхэттенского расстояния.
2. **Цель достижима из любой открытой клетки**, не проходя через штраф:
   всё, откуда пути нет, автоматически становится стеной. Поэтому при
   `gamma = 1` начальная BFS-политика proper и оценка не расходится.
3. **Штраф достижим из старта** — он создаёт реальный риск, а не висит в
   изолированном углу.
4. **Карта играбельна**: `isPlayable` реально обучает агента и проверяет, что
   его политика приводит из старта к цели и не зацикливается. Это отсекает
   вырожденные раскладки, где при `gamma = 1` выгоднее стоять на месте рядом со
   штрафом. Например, карта «штраф сразу за стартом» отвергается.
5. Вероятности нормированы: `intended + 2 * slip = 1`.

**Воспроизводимость.** `generate()` берёт новый случайный seed, `generate(seed)`
— заданный. Seed входит в `id` и в название среды
(`Случайная 5×5 · seed 7`), поэтому понравившуюся карту можно повторить:

```bash
java -cp out lab5.Main --random=7
```

Один и тот же seed всегда даёт одну и ту же карту: среда строится на
`java.util.Random`, а перебор вариантов в проверках детерминирован.

### Формат файла среды

```text
// Комментарии с // или ; допустимы.
name = Мой лабиринт
reward = -0.04
goalReward = 1
penaltyReward = -1
intended = 0.8        // вероятность запланированного хода
slip = 0.1            // вероятность сноса влево/вправо

map =
. . . . . G
. # # . # .
S . . . . .
. # . # # .
. . . . . P
```

Правила:

- карта задаётся строками сверху вниз; пробелы внутри строк игнорируются;
- символы: `.` — обычная клетка, `#` — стена, `S` — старт, `G` — цель,
  `P` — штраф; каждый из `S`, `G`, `P` должен встречаться ровно один раз;
- ширина и высота определяются по карте автоматически;
- вероятности должны удовлетворять `intended + 2 * slip = 1`;
- параметры `name`, `reward`, `goalReward`, `penaltyReward`, `intended`, `slip`
  необязательны — по умолчанию берутся значения классической среды.

Готовый пример лежит в [`my-environment.txt`](my-environment.txt).

> Замечание: сетка должна допускать путь от старта к цели. Иначе при
> `gamma = 1` оценка политики расходится — `SelfTest` и `validate()` такой
> среде не помогут, но `policyIteration()` сообщит об ошибке сходимости.

## Модель среды

### Сетка и координаты

Размеры задаются конфигурацией. Для классической среды ширина `4`, высота `3`
(совместимые константы `Environment.WIDTH` / `Environment.HEIGHT`).

- `State(row, col)`:
  - `row = 1` — нижняя строка, `row = height` — верхняя;
  - `col = 1` — левый столбец, `col = width` — правый.
- Проще говоря, это декартова сетка, где `row` — вертикальная ось (вверх), `col` —
  горизонтальная (вправо).

```text
row = 3:  (3,1)  (3,2)  (3,3)  (3,4)  <- цель
row = 2:  (2,1)  WALL   (2,3)  (2,4)  <- штраф
row = 1:  (1,1)  (1,2)  (1,3)  (1,4)
            ^
          старт
```

### Константы

Значения ниже — параметры **классической** среды (пресет `classic`). В других
средах они берутся из `EnvironmentConfig`.

| Константа / геттер | Значение classic | Смысл |
|-------------------|------------------|-------|
| `getWidth()` / `WIDTH` | `4` | число столбцов |
| `getHeight()` / `HEIGHT` | `3` | число строк |
| `getStart()` / `START` | `(1,1)` | стартовое состояние |
| `getGoal()` / `GOAL` | `(3,4)` | цель, `+1`, терминал |
| `getPenalty()` / `PENALTY` | `(2,4)` | штраф, `-1`, терминал |
| `getWalls()` / `WALL` | `{(2,2)}` | стены, вход запрещён |
| `getDefaultReward()` / `DEFAULT_REWARD` | `-0.04` | награда обычного состояния |

### Награды

```text
R(goal)   = goalReward    (по умолчанию +1.0)
R(penalty)= penaltyReward (по умолчанию -1.0)
R(стена)  = исключение IllegalArgumentException
R(прочее допустимое состояние) = defaultReward (по умолчанию -0.04)
```

Терминальные состояния **поглощающие**: `U(terminal) = R(terminal)`, будущая
полезность к ним не добавляется.

### Действия

`Action` содержит `UP`, `RIGHT`, `DOWN`, `LEFT`, `NONE`.

| Действие | `dRow` | `dCol` | Смысл |
|----------|--------|--------|-------|
| `UP` | `+1` | `0` | вверх (увеличение `row`) |
| `RIGHT` | `0` | `+1` | вправо |
| `DOWN` | `-1` | `0` | вниз |
| `LEFT` | `0` | `-1` | влево |
| `NONE` | `0` | `0` | остаться на месте (только терминалы) |

`Action.MOVES = [UP, RIGHT, DOWN, LEFT]` — порядок важен для tie-breaking:
при равных Q-значениях выбирается более раннее действие.

`left()` / `right()` возвращают направление после поворота на 90°; для `NONE`
возвращается `NONE`.

### Стохастические переходы

Для нетерминального состояния `s` и действия `a` используются вероятности из
конфигурации (по умолчанию классические):

- `intended` (по умолчанию `0.8`) — переход в `intendedNextState(s, a)`;
- `slip` (по умолчанию `0.1`) — переход в `intendedNextState(s, a.left())` (снос влево);
- `slip` (по умолчанию `0.1`) — переход в `intendedNextState(s, a.right())` (снос вправо).

`intendedNextState`:

- если `s` терминальное, заблокированное или `a == NONE` — вернуть `s`;
- иначе вычислить `(s.row + a.dRow, s.col + a.dCol)`;
- если выход за границу или стена — вернуть `s` (агент остаётся на месте);
- иначе вернуть новое состояние.

Если несколько вариантов ведут в одно и то же состояние, вероятности
**суммируются**. Например, для `(1,1)` и `DOWN`:

```text
0.8 -> (1,1)   (выход вниз за границу)
0.1 -> (1,2)   (снос вправо)
0.1 -> (1,1)   (снос влево, тоже граница)
итог: (1,1)=0.9, (1,2)=0.1
```

Для каждого нетерминального `(s, a)` сумма вероятностей равна `1.0`; это
проверяет `Environment.validate()` и `SelfTest`.

### Эталонные переходы для `(1,1)`

| Действие | Переходы |
|----------|----------|
| `UP` | `0.8 -> (2,1)`, `0.1 -> (1,1)`, `0.1 -> (1,2)` |
| `RIGHT` | `0.8 -> (1,2)`, `0.1 -> (2,1)`, `0.1 -> (1,1)` |
| `DOWN` | `0.9 -> (1,1)`, `0.1 -> (1,2)` |
| `LEFT` | `0.9 -> (1,1)`, `0.1 -> (2,1)` |

Именно эти значения проверяет `SelfTest`, а не формулы из PDF (там другой порядок
осей).

## Алгоритмы

### Параметры

| Параметр | Значение | Где задан |
|----------|----------|-----------|
| `gamma` | `1.0` | конструктор `Agent` |
| `epsilon` | `1e-9` | конструктор `Agent` |
| максимум итераций оценки | `10000` | `Agent.maxEvaluationIterations` |
| максимум внешних итераций | `1000` | `Agent.maxPolicyIterations` |
| порядок tie-break | `UP, RIGHT, DOWN, LEFT` | `Action.MOVES` |

### Оценка политики

Для терминалов полезность фиксируется: `U(s) = R(s)`.

Для нетерминальных состояний выполняется синхронное обновление:

```text
U_new(s) = R(s) + gamma * Σ_{s'} T(s, policy(s), s') * U_old(s')
```

Используется копия карты полезностей, поэтому обновление синхронное.
`delta = max_s |U_new(s) - U_old(s)|`; цикл останавливается при `delta < epsilon`.
Если за `10000` итераций сходимости нет — `IllegalStateException`.

### Улучшение политики

Для каждого нетерминального состояния:

```text
Q(s, a) = R(s) + gamma * Σ_{s'} T(s, a, s') * U(s')
policy_new(s) = argmax_a Q(s, a)
```

При равенстве Q сохраняется более раннее действие в порядке `MOVES`.
Для терминалов записывается `NONE`. Метод возвращает число изменённых состояний.

### Policy iteration

1. Сбросить `utility`, `policy`, счётчики и историю.
2. `initializeUtility()`.
3. `initializePolicy()` (BFS).
4. Цикл:
   - `evaluatePolicy()`;
   - `changes = improvePolicy()`;
   - добавить `changes` в `policyChangeHistory`;
   - `policyIterationCount++`;
   - если `changes == 0`, выставить `converged = true` и выйти.
5. Если за `1000` внешних итераций сходимости нет — исключение.

### Начальная политика через BFS

BFS идёт **от цели по обратным рёбрам** `intendedNextState`, не заходя в стену и
не включая штрафное терминальное состояние `(2,4)` как промежуточное. Для каждого
нетерминального состояния выбирается действие, ведущее в состояние с минимальной
BFS-дистанцией; при равенстве — первое по `MOVES`. Переход в `PENALTY` не
выбирается. Для терминалов политика — `NONE`. Если путь не найден, берётся первое
допустимое действие.

Это гарантирует, что при `gamma = 1` начальная политика proper и оценка не
расходится.

Замечание: начальная политика не обязана совпадать с финальной. Например, из
`(1,3)` BFS может сначала выбрать `UP`, а policy iteration затем исправит выбор на
`LEFT`, как в эталонной таблице.

### Value iteration

Используется только в `SelfTest` для перекрёстной проверки. Политику не меняет.

```text
U_new(s) = max_a [ R(s) + gamma * Σ_{s'} T(s, a, s') * U_old(s') ]
```

Терминалы остаются `R(s)`. Остановка при `delta < epsilon` или после
`10000` итераций. Возвращает число выполненных итераций.

### Детерминированный путь по политике

`Agent.getOptimalPath(start)` идёт по `policy` через `intendedNextState`
(без случайных сносов), пока не достигнет терминала. Защита:

- лимит шагов `WIDTH * HEIGHT * 10 = 120`;
- обнаружение цикла через `Set<State>` → `IllegalStateException`;
- старт и терминал включаются в путь;
- если старт терминальный — возвращается список из одного состояния.

- след перемещений агента — полупрозрачную линию и точки;
- текущее положение агента — оранжевый кружок.

Стрелки строятся из `agent.getPolicy(s)`, поэтому всегда совпадают с политикой.
Направления на экране: `UP` — вверх (уменьшение `y`), `DOWN` — вниз,
`LEFT`/`RIGHT` — по горизонтали. Пересчёт координат: `y = offsetY +
(height - row) * cell`, что даёт верхнюю строку сверху, `row = 1` снизу.

Anti-aliasing включён. Размеры шрифтов и элементов масштабируются от размера
клетки, поэтому окно можно растягивать.

### Смена среды

- Выпадающий список «Среда:» содержит встроенные пресеты и загруженные ранее
  пользовательские среды.
- При выборе пункта `switchEnvironment` пересоздаёт `Environment`, `Agent` и
  `GridPanel`; обучение сбрасывается (`trained = false`), агент ставится в старт.
- «Своя среда...» открывает `JFileChooser`, читает файл через
  `EnvironmentConfig.load`, проверяет его через `new Environment(config).validate()`
  и добавляет в список.
- «Случайная среда» вызывает `RandomEnvironment.generate()`, проверяет результат
  через `validate()` и добавляет новый элемент в список, делая его активным.
- Ошибки показываются в `JOptionPane`, выбор откатывается к прежней среде.
- Во время обучения список и кнопки загрузки/генерации заблокированы; при смене
  среды обучение не переносится, поэтому `done()` `SwingWorker` дополнительно
  проверяет, что обучался тот же экземпляр агента.

### Кнопки

#### «Обучение»

- Запускает `agent.policyIteration()` в `SwingWorker`, чтобы не блокировать EDT.
- На время обучения кнопки блокируются, статус показывает «Обучение...».
- `trained = false` и `GridPanel` не читает `utility`/`policy`, пока идёт обучение.
- По завершении: `trained = true`, сброс агента в старт, очистка следа, обновление
  панели и статуса с числом внешних итераций и итераций оценки.
- При исключении — сообщение в статусе и `JOptionPane`.

#### «Шаг»

- Доступна только после обучения и только если текущее состояние не терминальное.
- Выполняет ровно один `agent.step(currentState)`.
- Обновляет состояние, след, суммарную награду, статус.
- При достижении терминала кнопки шага/запуска блокируются.

#### «Запуск/Пауза»

- Запускает `javax.swing.Timer` с текущей задержкой (по умолчанию `450 мс`,
  настраивается ползунком «Скорость»); каждый тик — один шаг.
- Во время работы текст кнопки — «Пауза», при нажатии таймер останавливается.
- При достижении терминала таймер останавливается автоматически, текст
  возвращается к «Запуск».
- `Thread.sleep` в обработчиках не используется.

#### «Сброс»

- Останавливает таймер.
- Возвращает агента в старт, очищает след и суммарную награду, сбрасывает
  последнее действие.
- **Не удаляет** обученную политику и `U`.

### Строка статуса

Показывает:

- название активной среды;
- текущее состояние;
- последнее действие;
- суммарную награду (формат `%.2f`);
- число внешних PI-итераций;
- число итераций последней оценки;
- сообщение «ДОСТИГНУТА ЦЕЛЬ» или «ШТРАФ» в терминале;
- «политика не обучена», пока обучение не завершено.

### Потокобезопасность GUI

- Обучение — в `doInBackground()` `SwingWorker`.
- Обновление UI — в `done()` (EDT).
- Движение — по `javax.swing.Timer` (события приходят в EDT).
- Все Swing-компоненты создаются и изменяются в EDT.
- Пока `trained == false`, панель не обращается к картам агента, которые пишет
  фоновый поток.
- При смене среды создаётся новый `Agent`; `done()` сверяет, что обучался
  именно текущий экземпляр, и не применяет устаревший результат.

## Ключевые проектные решения

1. **`State` — record.** Даёт бесплатные `equals`/`hashCode`, что критично для
   использования в `Map<State, ...>`.
2. **Единый источник переходов.** `Environment.getTransitionProbabilities` — единственное
   место, где строятся вероятности. `Agent` и `SelfTest` используют его, а не
   дублируют формулы.
3. **Порядок осей `(row, col)`.** `row = 1` снизу. Это зафиксировано в модели и
   отрисовке; формулы из PDF с другим порядком осей не копируются.
4. **`gamma = 1` + BFS-инициализация.** Предотвращает расходимость из-за improper
   policy.
5. **Терминалы поглощающие.** В оценке и VI они не обновляются: `U = R`.
6. **Детерминированный порядок.** `Action.MOVES` задаёт tie-break; `LinkedHashMap`
   в переходах задаёт стабильный обход; `getQValues` тоже `LinkedHashMap`.
7. **Суммирование совпадающих переходов.** Упрощает и делает корректными
   вероятности при сносах в границу/стену.
8. **`StepResult` как DTO.** Отделяет алгоритм от GUI и упрощает отображение.
9. **GUI не блокирует EDT.** `SwingWorker` для обучения, `Timer` для движения.
10. **Честные статусы.** До обучения `U` не выдаются за оптимальные, стрелки не
    рисуются, статус говорит «политика не обучена».
11. **Среда как данные.** `EnvironmentConfig` описывает окружение, а `Environment`
    только исполняет это описание. Один и тот же `Agent` работает на любой карте,
    а смена среды в GUI — это пересоздание модели, а не переписывание кода.
12. **Скорость как свойство таймера, а не алгоритма.** Алгоритм `Agent.step`
    синхронный; темп задаёт только `javax.swing.Timer`, чью задержку меняет
    ползунок. Поэтому ускорение не влияет на результаты обучения.
13. **Генерация с проверкой, а не «пока не повезёт».** Каждая случайная карта
    проходит BFS-достижимость и реальное обучение (`isPlayable`), поэтому
    приложение никогда не показывает среду, на которой агент зацикливается.
14. **Seed как публичный контракт.** Seed входит в `id` и имя среды, так что
    любую случайную карту можно воспроизвести командой `--random=SEED` и
    обсудить в отчёте.

## Ограничения и точки расширения

### Ограничения

- Набор встроенных сред фиксирован (`classic`, `open`, `maze`, `wide`), но любую
  другую можно задать текстом в файле, через `EnvironmentConfig.parse` или
  сгенерировать (`RandomEnvironment.generate`).
- Случайная генерация не сохраняет карту на диск: чтобы повторить среду, нужно
  запомнить seed из её названия.
- Параметры генерации (размеры `4…8 × 3…6`, плотность стен `15…30 %`, набор
  вероятностей) заданы константами в `RandomEnvironment`.
- `gamma` и `epsilon` задаются в конструкторе `Agent`, но лимиты итераций —
  константы полей (можно изменить в коде).
- В GUI одновременно живёт одна среда и один агент; переключение среды
  пересоздаёт их.
- Нет сохранения/загрузки обученной политики на диск (сохранить можно только
  описание среды).
- Скорость движения задаётся только в GUI; консольный режим выполняет обучение
  без задержек.
- Нет графиков сходимости: история изменений политики доступна через API, но не
  визуализируется.
- `valueIteration` меняет `utility` агента (используется для сравнения в тестах);
  в GUI он не вызывается.
- В `SelfTest` кириллица может выглядеть искажённой в некоторых консольных
  кодировках Windows, но это не влияет на код возврата и результаты.

### Как расширять

- **Новая карта:** добавить текстовый файл и запустить
  `--env-file=...` либо загрузить его кнопкой «Своя среда...». Код менять не нужно.
- **Другой характер случайных сред:** поменять диапазоны размеров, плотность стен
  или набор вероятностей в `RandomEnvironment`.
- **Новый пресет в списке:** добавить статический метод в `EnvironmentConfig` и
  включить его в `presets()`.
- **Другая сетка/объекты в коде:** собрать `EnvironmentConfig` вручную; алгоритмы
  `Agent` менять не нужно, пока среда реализует те же методы.
- **Другая стохастичность:** задать `intended`/`slip` в конфигурации или
  переопределить `getTransitionProbabilities`; `Agent` подхватит автоматически.
- **Другие параметры обучения:** использовать конструктор
  `Agent(env, gamma, epsilon)`.
- **Q-learning / SARSA:** добавить отдельный класс, использующий
  `env.sampleNextState` и `env.reward`; `Environment` уже готов.
- **Новая визуализация:** заменить `Visualizer`, используя публичный API `Agent`
  (`getUtility`, `getPolicy`, `step`, `getQValues`, счётчики).
- **Больше проверок:** добавить вызовы `check(...)` в `SelfTest`; API уже
  возвращает всё необходимое.

## Диагностика проблем

### `javac`/`java` не найдены

Укажите полный путь к JDK, например:

```bash
"/mnt/c/Users/Kardfox/.jdks/openjdk-26.0.2.1/bin/javac.exe" -encoding UTF-8 -d out src/lab5/*.java
"/mnt/c/Users/Kardfox/.jdks/openjdk-26.0.2.1/bin/java.exe" -cp out lab5.SelfTest
```

### Windows JDK перестал запускаться из WSL

Проверьте интероп:

```bash
ls /proc/sys/fs/binfmt_misc/WSLInterop
```

Если файла нет — перезапустите WSL или включите WSL Interop.

### Консоль показывает «кракозябры»

Исходники и вывод — UTF-8. В некоторых консолях Windows кодовая страница не
совпадает. Это косметика; на результаты и код возврата не влияет. Можно
перенаправить вывод в файл и открыть его в UTF-8-редакторе.

### GUI не открывается

- Убедитесь, что запускается `lab5.Main` без `--test` и `--console`.
- При запуске из WSL через `java.exe` окно будет на стороне Windows.
- В средах без графики Swing выбросит `HeadlessException`; используйте
  `--console` или `--test`.

### Обучение «не сходится»

Проверьте:

- сумму вероятностей для всех `(s, a)`;
- поглощение терминалов (`U(terminal) = R(terminal)`);
- отсутствие переходов в стену/за границу;
- корректность BFS-политики (не ведёт в `PENALTY`);
- `gamma` и `epsilon`;
- лимиты `maxEvaluationIterations` и `maxPolicyIterations`.

### Путь в GUI отличается от детерминированного

Это нормально: GUI использует `sampleNextState` (случайные сносы), а
`getOptimalPath` — планируемый `intendedNextState`. Политика при этом одна и та
же.
